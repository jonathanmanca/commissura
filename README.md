# commissura

Turn raw clinical material — HL7 v2 lab messages, free-text reports, DICOM
imaging metadata — into a standardised, de-identified, research-ready dataset
with a verifiable manifest.

BIDS gives neuroimaging a shared layout. Nothing equivalent links laboratory
results and clinical reports to the same subject. `commissura` builds that bridge.

> **All clinical data in this project is synthetic.** No real patient data ever
> enters this repository, in any form. Every fixture is generated by
> `commissura generate`.

## Why

EU Regulation 2025/327 (European Health Data Space) makes secondary use of
health data a legal obligation for data holders from March 2029. Hospitals,
research institutes and laboratories will have to produce structured,
de-identified, documented datasets. `commissura` is a local command-line tool that
does exactly that — no service to deploy, no network component, no accreditation
required.

## What this will not do for you

Four limits, stated here rather than further down, because a tool that touches
health data should declare them before you install it and not after.

**It needs a structured source beside the free text.** The de-identification
here works by targeted redaction: the laboratory message *states* this patient's
name, national identifier and record number, MSH-4 states the sending
institution, OBR-16 the ordering clinician, the imaging header the institution's
address. So the problem stops being "find the names in the prose" and becomes
"remove these specific strings", which is exact, auditable and countable. Take
the structured source away and the method has nothing to work from. **If what
you have is a folder of PDF reports and nothing else, this tool is not for
you** — you would need named entity recognition, which this project rejects on
the evidence that general-purpose tools miss over half of clinical PHI. Rules
first, measurement always; and no rules are possible without a source of truth.

**Exact intervals are a re-identification channel, and this tool keeps them
exact on purpose.** The dataset carries `day_offset` from each subject's own
baseline, with no calendar anchor, because the interval between two events is
clinically useful and the absolute date is what has to go. The consequence:
anybody who learns **one** true date for a subject from anywhere else — a
discharge letter in a drawer, a dated post, an insurance claim, an obituary —
recovers that subject's entire timeline, because every other event is a known
number of days from it. Blurring the intervals would close the channel and
destroy the clinical value, so this tool does not do it. Decide which side of
that trade-off your release is on before you publish; it is the single most
likely route from this dataset back to a person.

**On a small cohort, k-anonymity does not reach a useful threshold, and no
amount of care changes that.** `risk` reports the number honestly and the
honest number is often 1: twenty-five people with exact ages cannot reach k=5
on age and sex together. That is arithmetic, not a defect in the dataset or the
tool. The fix is banding the ages or dropping an attribute before release, which
is a decision about your data that `commissura` does not take for you. Run
`commissura risk` and read the number before you release anything, and see
[`commissura risk`](#commissura-risk) for why k is a measurement and not a
certificate.

**Lose the key file and the dataset is permanently orphaned.** Not unreadable —
the data stays exactly as useful as it was — but no longer *extensible* or
*linkable*. You cannot add next year's records for the same people, because
their subject labels can never be derived again. You cannot link it to another
dataset you built, because you cannot show the labels came from the same secret.
You cannot answer a question about which original record a row came from. Every
pseudonym in the dataset derives from that one file, nothing in the dataset can
reconstruct it, and that is the design working as intended. Back it up
somewhere you will still have in five years.

## Install

Requires Python 3.11 or newer.

**Not published to PyPI yet**, so install from a checkout:

```bash
git clone https://github.com/jonathanmanca/commissura.git
```

```bash
cd commissura && uv venv && uv pip install -e .
```

Add the development extras to run the tests and the linters:

```bash
uv pip install -e ".[dev]"
```

hand.

`build` already ran this and would have failed if it did not conform. Running it

**The six warnings are the dataset telling you something true about itself.**
Six of its twenty-seven imaging studies say in their own metadata that
identifiers are rendered into the pixels — put there by the
`imaging.burned_in_annotation` defect, which is what a real scanner does when a
technician types a name onto a screen capture. This tool orchestrates `dcm2bids`

carried on purpose so that whatever converts the images knows to look.

A warning rather than an error, because the dataset is not malformed and
refusing to build would leave you worse off than telling you. It is a warning
rather than silence because a dataset nobody warned about is one somebody
converts without looking — which is how it behaved until the audit of
2026-11-13 found `conforms — 0 warnings` printed over a dataset in which every
study was flagged.

## Who a record belongs to

Everything downstream of this question depends on the answer, and nothing
downstream can tell when it is wrong. Targeted redaction removes the identifiers
your structured exports *declared for that subject*, so two people grouped under
one key leave only one set of identifiers to remove — and the other person's name
is never looked for. The policy is in
[`read/identity.py`](src/commissura/read/identity.py), which states its own
reasoning; the shape of it is:

**A subject is established by a validated national identifier, or by a record
number scoped to the institution that issued it.** The manifest says which, per
dataset, under `source.subject_keys`:

```json
"subject_keys": { "national_id": 25, "scoped_record_number": 0 }
```

A subject on the first kind is relinkable to another holder's export under the
same key. One on the second is not — a hospital's record number means nothing
outside it — so that number is worth looking at before you release.

**A missing identifier is never a shared one.** `UNKNOWN`, `N/A`, a row of
zeros, a wrong check character, the wrong length: each is reported by name and
none is ever an identity key. If your export fills an unavailable codice fiscale
with a sentinel, those records are keyed on their record numbers instead and you
get one `invalid_national_identifier` issue per record saying so.

**A record number is scoped to its assigning authority**, read from PID-3
component 4, or MSH-4, or DICOM `InstitutionName`. Two hospitals both number
their patients from 1, so an unscoped index attributes one site's imaging study
to another site's patient. Where one number is used by two people and the
authority cannot tell them apart, every record resolving through it is reported
as `ambiguous_record_number` rather than attached to a guess.

**What a report's header declares is removed too, and a disagreement is
reported.** A laboratory message states the patient in PID-5; a report states
them in its own header, and the two can disagree — a mis-filed document, which
happens in any export. Both now reach redaction, so a report naming somebody
else does not publish that name. And when the name shares no word with any name
the subject is known by, you get a `conflicting_report_name` issue, because a
name that disagrees can mean the document belongs to a different patient and no
amount of redacting makes that right.

The comparison is on the *set* of words, folded, so `ROSSI MARIO` against
`MARIO ROSSI` is not a conflict and nor is an abbreviated given name, a middle
name present in one source only, or a surname written with and without its
space. Each of those is one person recorded twice far more often than two
people confused, and crying wolf on them would bury the case the check exists
for.

**The codice fiscale is validated, including omocodia.** When two people would
be assigned the same code the Agenzia delle Entrate substitutes letters for
digits, so a validator that only checks the checksum rejects genuine
identifiers. Any other national scheme — an ENI or STP code, another country's
identifier — fails validation and falls back to a scoped record number. That is
a real limitation and is why `subject_keys` is in the manifest.

## Bringing your own data

Nothing in `build` depends on the generator. `read_corpus` does three globs and
reads whatever it finds, so a corpus exported from a real system works — if it
is laid out the way the reader looks for it, and if the documents carry the
labels linkage needs. Both are undocumented until this section, which is a
problem, because getting them wrong fails *quietly*.

```
raw/
  lab/        *.hl7    HL7 v2 messages, one per file
  reports/    *.txt    free text, UTF-8
  imaging/    *.json   DICOM JSON Model (PS3.18) metadata, one array per study
```

Those three patterns are the whole contract. Subdirectories are not searched,
other extensions are ignored, and the `_generator/` directory a generated
corpus carries is only read by `commissura measure`.

### What each kind of file has to carry

**A laboratory message establishes a subject, so it needs an identity.** The
reader wants a national identifier: in the PID-3 identifier list with type code
`NNITA` or `NI`, or failing that in PID-19. A message with neither is reported
as `unreadable_lab_message` and the person it describes does not exist as far
as the rest of the run is concerned. PID-3 with type code `MR` supplies the
record number, which is the only thing imaging can be linked on. The rest is
read where present and skipped where not: MSH-4 the sending facility, OBR-4 the
panel, OBR-7 the collection time, OBR-16 the ordering clinician, OBX the
results.

**A report is linked by the labels in its header.** Lines of the form
`Label: value`, matched exactly:

| Label | Used for |
| --- | --- |
| `Codice fiscale` | the national identifier — tried first |
| `Numero nosografico` | the record number — the fallback |
| `Data del referto` | which session the report belongs to |
| `Paziente` | the patient's name, so the scrubber can remove it |

A line reading `Dott. SURNAME NAME` is taken as the signature, and it is the
**only** structured source for the report's author: no laboratory message names
the clinician who wrote a report, so without it that name cannot be redacted
anywhere it appears.

**Imaging is linked on `(0010,0020)` PatientID**, compared to the record number
with leading zeros stripped. `(0008,0020)` StudyDate decides the session.

Dates are accepted as `YYYYMMDD`, `YYYYMMDDHHMM`, `YYYYMMDDHHMMSS`,
`DD/MM/YYYY`, `DD.MM.YYYY` or `YYYY-MM-DD`.

### The two silent failures, and how to see them

**Labels the reader does not recognise mean every report is unlinked.** If your
template writes `Paziente / Patient` or `CF` or nothing at all, no report
attaches to anybody, every one of them is reported as `unlinked_report`, and
the dataset builds successfully with no reports in it. That reads as "the tool
does not work" and is in fact the tool telling you precisely what is wrong, in
a place you have not looked yet.

**A linked record with no readable date is dropped too**, and that one used to
be genuinely silent. Sessions are dated encounters, so a report whose
`Data del referto` cannot be parsed, or an imaging study with no StudyDate, has
nowhere to go. It is not a linkage issue, because linkage succeeded — so until
this was fixed nothing said anything at all, and the only evidence was a file
count lower than the number of files you handed over.

Both are now counted where you will see them:

```
  linkage issues         0
  records dropped        0  (no readable date)
```

**The paths are printed by `build` and nowhere else.** An export names its
files after the record they hold, so `lab/6895111_LAB17546198.hl7` carries a
medical record number in its name, and a list of them is a list of patient
identifiers. `.deident/manifest.json` is written to be sent to an access body,
so it counts them by reason instead — `source.linkage_issues` for records that
could not be attached to anybody, `source.records_dropped` for records that
were attached and then had nowhere to go, and
`source.records_not_in_dataset` adding them up. Two lists rather than one
because they need different fixes: the first is a labelling problem in your
export, the second a date format the reader does not recognise. Your terminal
gets the filenames; the document that travels gets the counts.

A dropped record carries one of two reasons. `undated_record` names the field
that should have held a date. `subject_has_no_dated_event` is worse and is
reported separately for that reason: nothing in that person's records carries a
readable date, so there is no baseline to express offsets from, *every* one of
their records drops — and a row still appears in `participants.tsv`, so the
dataset claims a participant it holds nothing for.

The labels live in one table, `_REPORT_LABELS` in
[`read/corpus.py`](src/commissura/read/corpus.py), for exactly this reason:
adapting to another hospital's template is an edit there rather than a rewrite
of the reader.

## Commands

| Command | What it does | Status |
| --- | --- | --- |
| `commissura generate` | Write a synthetic raw clinical corpus, with injectable defects and ground-truth PHI annotations | available |
| `commissura defects` | List the defects the generator can inject, and the real-world cause of each | available |
| `commissura validate` | Check a dataset against the layout and report what is missing | available |
| `commissura rules` | List every validation rule and what it checks | available |
| `commissura keygen` | Create a pseudonymisation key | available |

| `commissura risk` | k-anonymity over participant attributes, flagging k < 5 | available |

| `commissura measure` | Compare the generator's ground truth against the built dataset | available |
| `commissura whois` | Derive the subject label a real identifier was given | available |

Every command that reports anything accepts `--json`, so the tool composes
inside somebody else's pipeline without being screen-scraped.

A test pins this table against the names the CLI actually registers — both
directions, so a command missing from it fails and a row claiming one that does
not exist fails too. A table that lists what the tool does is worth nothing if
it can quietly stop being true, and this one went stale once in the document it
used to live in.

### `commissura generate`

```bash
commissura generate --subjects 25 --seed 42 --out ./raw
```

Produces a corpus that looks like three separate hospital exports, because that
is how such data actually arrives — and linking them is the problem this project
exists to solve:

```
raw/
  lab/        ORU^R01 messages, one file per panel
  reports/    free-text radiology and discharge reports
  imaging/    DICOM-style metadata sidecars
  _generator/
    generation_manifest.json   seed, counts, tool versions, defects applied
    phi_annotations.json       every identifier, with file and character offsets
```

The generated material **deliberately contains synthetic identifiers** — names,
codici fiscali, absolute dates, addresses, referring physicians. That is the
point: you cannot test a de-identifier on data that has nothing to remove.

`phi_annotations.json` is the ground truth. Because the generator records where
it put every identifier, de-identification recall becomes measurable rather than
assumed — which matters, since general-purpose LLM tools have been shown to miss
over half of clinical PHI.

Offsets are character positions into the UTF-8 decoded file, over a half-open
interval, so `text == content[start:end]` always holds. `--verify`, on by
default, re-reads every file from disk and checks it.

#### Reproducibility

The same seed and the same tool version always produce the same corpus, and the
guarantee is stronger than that:

```bash
commissura generate -n 3  --seed 11 -o small
commissura generate -n 30 --seed 11 -o large   # the first 3 subjects are identical
```

Subject *n* does not depend on how many subjects were requested, because each
one is generated from its own stream derived from the master seed. So a bug
report that says "subject 347 has a negative haemoglobin" stays reproducible
from the seed alone, without shipping the corpus.

#### Defect injection

`--defect-rate` controls the probability that any given defect opportunity is
taken. Every injected defect is recorded in the manifest with the file it landed
in, which is what makes validator development measurable: run the validator,
compare what it reported against what was injected, read off the misses.

`--defect-rate 0` produces undamaged data — but not *easy* data. Identifiers
written inside clinical sentences are how reports are written, not a defect, so
they are always present. Anyone who scrubs the header fields of a clean corpus
and scores perfectly has learnt something useful.

### `commissura validate`

```bash
commissura validate ./dataset
```

Reports everything it finds rather than stopping at the first problem. The
question the command answers is *what is missing*, in the plural, and a
validator that answers one item at a time turns a single review into a dozen
round trips.

```
ERROR   DS002 participants.tsv: required file participants.tsv is missing from the dataset root
        Every dataset must carry participants.tsv.
ERROR   DI003 sub-a3f9c21b4e07/ses-01/reports/sub-a3f9c21b4e07_ses-01_run-01_report.txt:
        contains what looks like an absolute date: '12/03/2023'
        A date written inside a sentence is invisible to field-based scrubbing.

NOT CONFORMANT: 2 error(s), 0 warning(s), 0 notice(s) from 40 rules
```

Exits 0 when the dataset conforms and 1 when it does not. Warnings do not affect
the exit code unless `--strict` is passed: a dataset can conform and still have
things worth improving, and a validator that rejects for stylistic reasons gets
switched off.

`commissura rules` prints the whole rule set. **The rule set is the schema** —
there is no separate specification document to drift out of date.

| Prefix | Rules | What they check |
| --- | --- | --- |
| `DS` | 10 | The skeleton: required files, the dataset description, the manifest |
| `PT` | 9 | `participants.tsv`, and its agreement with the directories on disk |
| `NM` | 6 | Directory and file naming, and the BIDS entity grammar |
| `LB` / `RP` | 6 | The `lab` and `reports` datatypes this project adds |
| `DI` | 8 | The de-identification invariants the layout promises |

The `DI` rules are the ones that justify the command existing, and they are
written as *structural* requirements rather than as advice. A dataset carrying a
real calendar date is not weakly de-identified, it is malformed, because the
layout states that time is expressed only as `day_offset` from each subject's
own baseline. Intervals stay exact; the calendar anchor is gone.

`DI003` is the one that earns its keep: it scans report prose, where a date
inside a sentence — *si confronta con il precedente esame del 12/03/2023* — is
invisible to anything that scrubs by field.

#### Written before `build`, on purpose

`validate` exists before the command that produces datasets. That ordering
forces the schema to be precise: the layout lives in one module,
[`commissura/layout.py`](src/commissura/layout.py), and the validator is derived
from it, so `build` will have a specification to satisfy instead of defining one
by accident as it goes.

```
dataset/
  dataset_description.json
  participants.tsv
  sub-<label>/ses-<n>/
    anat/ pet/ lab/ reports/
  derivatives/
  .deident/
    manifest.json
    risk_report.json
```

`lab/` and `reports/` are the extension. They follow BIDS naming rather than
inventing new rules, so a BIDS validator will not recognise them and will not be
confused by them either.

### Pseudonymisation

One secret key, everything derives from it, the key never enters the dataset.

```bash
commissura keygen --out ~/.commissura/key
export COMMISSURA_KEY_FILE=~/.commissura/key
```

```
subject_id  = HMAC-SHA256(key, "subject|" + national_id)[:12]   -> sub-a3f9c21b4e07
date_offset = HMAC-SHA256(key, "offset|"  + subject_id) % 730 - 365
dicom_uid   = "2.25." + int(HMAC-SHA256(key, "uid|" + original_uid))
```

Three properties, each with a tempting wrong alternative:

**Keyed, not plain.** `sha256(national_id)` would be useless. A codice fiscale
encodes a name, a birth date, a sex and a place of birth, so the space is small
enough to enumerate: anyone with a candidate list hashes it and reverses the
dataset over a weekend. With an HMAC they need the key.

**Domain-separated.** Every derivation prepends a label naming what is being
derived. Without it, the same string used as a patient id and as an accession
number would produce the same pseudonym, and a value observed in one role could
be replayed in another.

**Deterministic across runs and modalities.** The same person gives the same
`sub-` label today and in three years, in the lab branch and the imaging branch.
That is the only thing linking three separate hospital exports.

Subject labels keep 48 bits of the digest. Collisions are a theoretical concern
rather than a practical one, but the pseudonymiser records what it has issued
and **raises** on a collision rather than silently merging two people.

#### The key is never a command-line argument

There is no `--key <value>` option, here or anywhere. A key passed as an
argument lands in shell history, in `ps` output for every other user on the
machine, and in the logs of any CI system that runs the command. The only ways
in are a key file and an environment variable naming that file — not holding the
key, since the process environment is readable from `/proc` and gets dumped
wholesale into crash reports.

What is printed and recorded is the key's **fingerprint**: a domain-separated
digest that identifies the key without carrying it. It answers the question
somebody asks years later — were these two datasets built from the same key, and
are they therefore linkable? — without answering what the key is.

On POSIX the key file is created mode 0600. On Windows that mode is largely
ignored, so `keygen` reports `owner-only access NO` and says what to do instead,
rather than implying a protection it did not apply.

#### Two different time mechanisms

| | What it is | Where it appears |
| --- | --- | --- |
| `day_offset` | Integer days from the subject's own baseline. Needs no key — it is a subtraction. | **In the dataset.** The only time representation it carries. |
| `date_offset` | Per-subject ±365-day HMAC shift. Preserves intervals exactly, destroys the calendar anchor. | **Never in the dataset.** For values that must stay a syntactically valid date for a downstream tool, notably DICOM `StudyDate` on the way into `dcm2bids`. |

The shift differs per subject deliberately: one offset for the whole cohort
would preserve cross-subject alignment, and a single known date anywhere would
then unshift everybody.

### `commissura build`

The walkthrough above runs this end to end. In full, with every value the
profile requires and the tool will not invent:

```bash
commissura build ./raw --out ./dataset --key-file ~/.commissura/key \
    --hdab "<the access body governing this dataset>" \
    --publisher "<your organisation>" \
    --contact-point "<an address somebody can write to>" \
    --access-url "<where a request for this data would go>" \
    --dataset-type SYNTHETIC_DATA
```

Reads the three exports, links them to the same people, derives every pseudonym
from one key, expresses dates only as offsets from each subject's own earliest
event, scrubs the free text, and writes a BIDS-shaped dataset with two
accompanying documents. Then it validates its own output and fails if the result
does not conform.

#### Free text is de-identified by knowing what to look for

The usual approach to clinical prose is named entity recognition: read the text,
work out which words are names. This does something different, and it is only
possible because the corpus was **linked first**.

The laboratory message states this patient's name, national identifier and
record number. MSH-4 states the sending institution. OBR-16 states the ordering
clinician. The report's own signature line states who signed it. The imaging
metadata states the institution's street address. So the problem stops being
*find the names* and becomes *remove these specific strings* — exact, auditable,
and reportable.

That is the argument for linking modalities before de-identifying them, and the
opposite order is the intuitive one.

A report comes out like this:

```
[INSTITUTION]
[ADDRESS] - [ADDRESS]

REFERTO DI DIAGNOSTICA PER IMMAGINI

Paziente: [NAME]
Nato/a il: [BIRTH-DATE]   Eta: 62 anni
Codice fiscale: [NATIONAL-ID]
Data del referto: [day_offset:+0]

REPERTI
Non segni di sanguinamento intra o extra-assiale.
Si confronta con il precedente esame del [day_offset:-41] eseguito presso [INSTITUTION].
```

The clinical narrative survives intact. The comparison interval survives as an
offset, because *41 days earlier* is clinically useful while *12 March 2023* is
a calendar anchor. **The birth date is removed, not offset**: an offset from the
subject's own baseline would state the birth date exactly in a dataset that also
carries the baseline, which protects nothing.

What the method cannot reach is printed, not scored:

```
  Residual risk the method cannot reach:
    1 unrecognised all-capitals token(s) remain, of 4 characters. Nothing
    declared them, so this is the layer that catches what was not
    anticipated. Not quoted here: this report travels with the dataset.
```

A score invites a reader to treat de-identification as solved above some
threshold. A list tells them where to look.

**Three layers, and only the first is certain.** The detector used to match
``[A-Z]{4,}`` and nothing else, which meant it reported ``FRANCESCA FONTANA``
and said nothing at all about ``Francesca Fontana`` — so a template writing
names in title case would have left a leaked name completely silent.

| Layer | Question | False positives |
| --- | --- | --- |
| Declared values | Did a string we were told to remove survive? | None possible: these were handed to the scrubber by name |
| Position | Is something still sitting where a name is *declared* to be, after ``Paziente:`` or ``Dott.`` ? | Bounded by the label table, not by guessing at names |
| Unanticipated tokens | Is there a word nothing declared that looks like an identifier? | The noisiest layer, and the only one that can see what you did not tell us about |

All three are case-insensitive and accent-insensitive: matching is NFKD-folded,
so ``Fontanà`` and ``FONTANA`` and ``fontana`` are one needle. None of them
quotes what it found, because this list travels in the manifest.

**It is a measurement and not a clearance.** A detector that reports nothing has
reported nothing; it has not established that a document is free of identifiers.
The counterpart is `commissura measure`, which asks the opposite question —
whether the identifiers the generator planted survived — and the two fail
differently on purpose. Layer two depends on a label table, so a hospital
template using labels this tool does not know gets layers one and three only;
that is the same dependency `_REPORT_LABELS` has, now stated rather than
implied.

#### A build publishes exactly what it produced

Everything is assembled in a staging directory beside the destination and moved
into place at the end. So **a rebuild replaces the dataset rather than writing
over it**, which is what makes a withdrawal work:

```bash
# A patient objects. Remove their records from the corpus and rebuild.
rm raw/lab/1787493_* raw/reports/1787493_* raw/imaging/1787493_*
commissura build ./raw --out ./dataset --key-file ./commissura.key \
  --hdab "..." --publisher "..." --contact-point "..." --access-url "..."
```

The withdrawn records are gone from the dataset and from the manifest. Before
this was staged, they were not: the build wrote over what it happened to
overwrite and left the rest, reported `conforms` with exit code 0, and
`commissura verify` then certified the result as `INTACT` for as long as the
dataset existed.

**A destination that is not empty and is not a commissura dataset is refused.**
A directory holding no `.deident/manifest.json` and no
`dataset_description.json` is somebody else's, and there is no flag to override
that — the flag would exist only so that a mistyped `--out` could reach your
documents.

A failed build leaves the destination exactly as it was. Publication itself is
two renames rather than one atomic operation, because no portable call can
rename over a non-empty directory; if the second fails, the previous dataset is
put back and the message says where the finished build is.

**Nothing is removed that this tool did not write.** Both working directories
are created with `mkdtemp` beside the destination — random name, mode `0700`,
atomic — and each carries a marker naming the destination it is for. Every
removal verifies that marker first, so ownership is never established from a
path. A directory without one is refused and left alone, and a working
directory left behind by an interrupted build is visible, named, and says in
its own marker what it was for.

Two builds publishing to the same destination are not serialised: each has its
own working directory and each rename is atomic, so the destination always holds
one *complete* dataset and never a mixture, but which one wins is undefined.
Locking would be the fix if this were a service rather than a command somebody
runs on a folder.

#### Two documents, two readers

| File | Schema | Reader |
| --- | --- | --- |
| `.deident/manifest.json` | This project's own. No standard covers it. | Whoever audits the de-identification |
| `healthdcat-ap.jsonld` | HealthDCAT-AP Release 8, as JSON-LD | A Health Data Access Body, and any catalogue |
| `dataset_description.json` | BIDS | Tools that read the dataset |

HealthDCAT-AP describes a dataset *for a catalogue* — title, theme, access
rights, legal basis, retention period. It carries nothing about what was done to
de-identify the data, so that is a separate document with a separate version.

`--hdab` has no default and is not invented. The profile makes
`healthdcatap:hdab` mandatory at exactly one value, and Italy has not designated
its Health Data Access Body yet, so a dataset naming none is the normal case
until 2027. The command builds anyway and says what is missing:

```
  Not yet conformant. Mandatory properties with no value:
    healthdcatap:hdab
    Supply them with --hdab and --publisher.
```

#### A page to read it with

```bash
commissura build ./raw --out ./dataset --key-file ./commissura.key \
    --hdab "..." --publisher "..." --contact-point "..." --access-url "..." \
    --report ./review.html
```

Everything the dataset records is already on disk, in JSON, for a machine.
Comparing a report before and after de-identification is the one check nobody
can automate — the question is "did the clinical content survive", and a
scrubber that removed the medicine would protect a useless dataset — and until
now it meant opening two files in two windows and reading across. `--report`
writes a single self-contained HTML page: the build summary, a few reports side
by side, redaction counts by category, the manifest's field table, the residual
risk and the k table. No server, no state, no key. It opens offline and keeps
working when this tool is gone.

**It contains patient data, and it is the only output of `commissura` that
does.** The "before" half of each comparison is an unredacted clinical report.
That is the point of the page and it makes the file something that must stay
inside your organisation, so:

- **it is never written inside the dataset directory, and the command refuses
  rather than warning.** A file there would be digested into the manifest's own
  integrity list and released with the dataset. `--report ./dataset/report.html`
  is the obvious thing to type and is exactly the mistake;
- the page says what it holds in its first screenful;
- you name the file, because there is no safe default place for something that
  must not be filed with the dataset;
- it is opt-in, and stays opt-in.

```
  html report            /home/you/review.html
                         CONTAINS PATIENT DATA - do not release it
```

#### The field table is observed, not declared

The manifest's per-modality table is derived from the run. Every field the input
actually carried is listed with the number of files that held it, so a field
nobody anticipated is accounted for rather than going unmentioned:

```json
{ "field": "00100030", "name": "PatientBirthDate",
  "disposition": "removed", "files_present": 13 },
{ "field": "0020000D", "name": "StudyInstanceUID",
  "disposition": "replaced", "files_present": 13,
  "note": "as an HMAC-derived UID under the 2.25 arc" },
{ "field": "00290010", "disposition": "removed", "files_present": 3 }
```

That last row is a private vendor tag, present in three of thirteen files
because a defect put it there. Nothing declares it; it is in the table because
it was in the data, and an odd DICOM group number means its meaning belongs to
the vendor and is in no dictionary.

This works because **the build carries a whitelist, not a blacklist**: the lab
branch writes nine columns and the imaging branch seven keys, and everything
else is dropped by never being copied. So removal needs no list — only the
carried fields are declared, and whether each one passes through the
pseudonymiser, which is a fact about the code rather than about the data. A
`replaced` value is still relinkable by whoever holds the key; a `kept` value is
the original.

A label this tool does not recognise is reported as a class rather than
quoted, because a header label from somebody else's template is written beside
the value it labels and is a line of the input:

```json
{ "field": "other labelled lines", "disposition": "removed", "files_present": 49 }
```

That row is how you find out your template carries fields this tool never saw —
the same signal as reports landing in `records_dropped`, in the table rather
than in a count.

A report's prose body is not a field, so the reports modality carries a second
table beside the first, with the same three-way vocabulary:

```
category           disposition   documents   occurrences   marker
institution        removed              19           170   [INSTITUTION]
date               replaced             19            34   [day_offset:N]
date_of_birth      removed              19            19   [BIRTH-DATE]
provider_name      removed              14            29   [PROVIDER]
contact            removed               6            12   [CONTACT]
age                replaced              0             0
```

Both counts are there because for prose they answer different questions:
`documents` is coverage, `occurrences` is how many identifiers the method
actually found. `date_of_birth` sits with the removed and not with the dates on
purpose — an offset from the subject's own baseline would state the birth date
exactly in a dataset that also carries the baseline.

`contact` covers 6 of the 19 documents, because a discharge letter carries a
follow-up contact and a radiology report has no reason to. That partial coverage
is the point of counting documents separately from occurrences.

The row at zero is a rule that did not fire in this corpus — twenty-five people
produced nobody above the age ceiling — reported rather than omitted, because an
omitted row reads as "no such rule". The first run of this table had `contact`
at zero too, and that *was* a finding: the generator never wrote an email or a
telephone number into a report body, so the contact rule and the ordering fix
behind it were exercised by one unit test and by no corpus the tool produced.
A generated discharge letter now carries one, in prose rather than in a labelled
field, so only the patterns can find it.

#### Linkage is accountable

A subject exists only if a laboratory message established it, because the HL7
message carries the national identifier and a DICOM header does not. Every
record that cannot be attached produces an issue naming the file and the reason,
and the count goes into the manifest — it is the number to look at before
trusting a dataset.

**Where that identifier sits is not one answer.** The reader looks in the PID-3
identifier list first, for a repetition whose type code is `NNITA` or `NI`, and
falls back to PID-19. PID-19 was deprecated in HL7 v2.3.1 and an Italian
installation carries the codice fiscale in PID-3 with a type code — but
deprecated is not switched off, and plenty of interfaces still send it there. A
generated corpus contains both forms, one site per interface, because a fallback
no corpus exercises is a fallback nobody has tested.

The type code is worth a sentence of its own: **HL7 v2 table 0203 has no
concrete code for Italy.** It documents a pattern, `NNxxx`, "National Person
Identifier where the xxx is the ISO table 3166 3-character (alphabetic) country
code", so `NNITA` is that pattern instantiated rather than a listed concept.
`NI`, "National unique individual identifier", is listed, and some systems use
it instead. The reader accepts both; the writer emits `NNITA`.

Record numbers are compared with leading zeros stripped, which recovers the
`imaging.mrn_format_drift` defect: at `--defect-rate 1.0` across twenty
subjects, no imaging study is lost. That defect is the one that silently halves
a cohort when somebody joins on the raw identifier.

#### And over the laboratory values

```
  laboratory values      60 subject(s)
  analyte-value combos   478
  below k=5              469  (98.1% of combinations)
  minimum k              1
```

The same question as age and sex, asked of a column nobody calls identifying. A
haemoglobin of 13.2 that nobody else in the cohort shares is a handle on
whoever has it, for anyone who knows that one value — and a clinician, a
relative or a previous employer may well know it.

Counted **per subject, not per row.** The same person measured three times at
the same value is one person; counting rows would report a patient with frequent
bloods as *less* identifiable than one with a single test, which is backwards.

**98.1% of 478 combinations on sixty subjects, and tripling the cohort moved
that figure by two points.** That is the real finding and it is not a defect in
the dataset: a measured value is a near-unique quantity, not a category, so
almost every analyte-and-value pair belongs to one person. **Full k-anonymity
over continuous multivariate clinical data is not reachable, and no cohort size
gets you there.**

That is worth saying plainly because it explains the shape of the whole
regulation. The EHDS does not protect secondary use by requiring anonymisation —
it protects it with **data permits and secure processing environments**, because
for data like this anonymisation is not on the table. This report is a
measurement handed to whoever makes that judgement, and it is never a
certificate of anonymity.

**It reports and does not correct**, which is a decision rather than an
omission. Every remedy damages exactly what the data is for:

| Remedy | Why not here |
| --- | --- |
| Suppressing rare rows | The unusual value is both the risk and the reason somebody wants the dataset |
| Top and bottom coding | Removes the extremes, which is where the clinically interesting cases live |
| Rounding into bands | Same, more quietly: a creatinine banded to the nearest whole number is a different measurement |
| Adding noise | Worse in a clinical setting than most — an analyst who cannot say how far wrong their numbers are cannot reason about them at all |

Which of those is acceptable depends on the permit, the recipient and the
release arrangement, and only the data holder knows those. So `commissura`
measures, and the choice stays with the person who has to defend it.

The listing is capped at fifty combinations while the count stays exact: a
complete list would be the dataset again with its rarest values highlighted,
which is a worse artefact than the dataset, written into a file that travels.

### `commissura verify`

```bash
commissura verify ./dataset --key-file ./commissura.key
```

```
  files checked          52
  altered                0
  missing                0
  added                  0
  manifest               authentic

  INTACT: every recorded file matches its digest.
```

The manifest says what was done to the data. On its own it does not say the data
has not changed since — anybody can edit a value in a lab table or paste a name
back into a report, and the manifest goes on reading as though it were still
true. `build` records a SHA-256 per file it produced; this recomputes them and
reports what is altered, missing or added. It is the mirror of the check
`generate` already runs on its own output, where the recorded PHI offsets are
re-read from disk rather than trusted.

**What it proves depends on whether you have the key.** The digest list lives in
the manifest, so whoever can change a report can change the list beside it. The
digests catch the things that happen by accident: a TSV opened in a spreadsheet
and saved back, an incomplete copy, a stray export dropped into the tree. The
manifest also carries an HMAC over its own content, keyed by the secret, and
`--key-file` checks it — that is the part that catches a deliberate edit:

```
  manifest               DOES NOT MATCH ITS OWN TAG

  TAMPERED: the manifest does not match its own authentication tag, so its
  contents were edited after the build.
```

Zero files differing *and* a failed tag is the signature of somebody adjusting
the manifest to cover their tracks, which is why the two are reported apart.
Without `--key-file` the output says "not authenticated" rather than anything
reassuring: unchecked and checked-and-fine must never read the same way.

### `commissura measure`

```bash
commissura measure ./raw ./dataset
```

```
  category          planted  measured  removed  survived
  accession             314       314      314         0
  address               525       525      525         0
  age                   132        84       84         0  (kept by design)
  contact               268       268      268         0
  date                  523       523      523         0
  device_id             168       168      168         0
  institution           322       250      250         0
  national_id           163       163      163         0
  patient_id            258       258      258         0
  person_name           376       371      371         0
  provider_name         437       432      432         0
  uid                   168       168      168         0

  recall                 100.00%  of 3440
  survived               0
  too short to measure   58  (under 4 characters)
  declared by the holder 72  (publisher, HDAB, title)
  records not included   13  (their identifiers are absent because the record is,
                                 not because redaction removed them)
  dataset files searched 197
```

**100% of 3,440 measurable planted identifiers removed**, on the corpus the
walkthrough above builds. That number is the point of this project. "Rules
first, measurement always" is easy to write and the measurement half was a
promise until this command existed: the generator had been recording every
identifier it planted, with the file and character offsets, and nothing had
ever compared that record to the output.

The ground truth is the unusual part. Real corpora are annotated by hand,
partially, expensively, and the annotation is itself uncertain. Here it is a
by-product of writing the text, so it is complete by construction — and a
measurement is only ever as good as what it is measured against.

**Three exclusions, each visible in the output rather than folded into the
number.** Spans under four characters are not counted either way: a two-letter
fragment of a surname matches inside "de-identification", so calling it a leak
invents one and calling it removed invents a success. Ages are kept on purpose
and reported apart. And strings the holder typed on the command line — the
publisher's name, the HDAB — are excluded, because a hospital publishing its
own data names itself in the description, and that name is also written across
every report in the corpus; it is in the output by the holder's decision, not
because redaction failed.

**A fourth number that is a caveat and not an exclusion.** `records not
included` counts identifiers in records the dataset left out — here the
thirteen reports with no readable date. Their identifiers are absent because
the record is absent, which is no evidence that redaction works: in the
degenerate case a build that dropped everything would score a perfect recall
for producing nothing. It is reported beside the figure rather than subtracted
from it, because attributing it span by span would need the file paths, and
those are deliberately not in the manifest.

**And one limit no exclusion fixes.** This asks whether the *exact* planted
string survived. Half an institution name surviving is not a miss here and
never will be. That question is answered by the scrubber's residual-risk list,
which works the other way round — it looks at the output for anything shaped
like an identifier, without knowing what was planted. The two fail differently
on purpose and a reader needs both.

#### On a corpus with injected defects, it is not 100%, and that is the finding

```bash
commissura generate --subjects 5 --seed 23 --defect-rate 0.6 --out ./rough
```

Recall drops to **98.45%**, and every survivor is a clinician's name in a
report. The cause is two defects meeting: `reports.missing_author` removes the
signature block, which is the only structured field naming that clinician, and
`reports.identifier_in_prose` leaves them named mid-sentence in the body.
Targeted redaction cannot reach a name nothing declared.

That is the method's documented limit with a number attached to it rather than
a caveat in prose. Closing it would mean named entity recognition, which this
project rejects on the evidence that general-purpose tools miss over half of
clinical PHI. So the test suite pins the clean corpus at 100%, pins the
defective one above 95%, **and pins that every survivor is a person's name in a
report** — because a bound alone would stay green while the failure changed
character into something that is a defect rather than a limit.

#### What it found on its first run

Two leaks, neither visible by reading the code:

- **The manifest recorded the corpus's absolute path**, which on any ordinary
  machine contains the operator's account name, inside the one document written
  to be sent to an access body. A generated clinician who happened to be called
  JONATHAN is what made it visible. It now records the directory's name.
- **The residual-risk list quoted the tokens it was warning about.** A patient's
  surname appeared in `.deident/manifest.json` of a dataset from which every
  other trace of it had been removed — the document saying "I could not remove
  these" was handing them over. It now reports a count and a length range, and
  the file path tells a reviewer where to look.

Two more came later, from an audit that went looking for the same pattern a
fourth time — *for every field of the manifest, can it carry something derived
from the input?* It could, twice. A linkage issue and a dropped record each
carried a `detail` sentence built from the file that failed, so an unlinked
report put a codice fiscale in the document, and an unreadable file put a path
and an exception message there. Both are now counted by reason, and `build`
prints the paths to the terminal, which does not travel. The shape had been
wrong since linkage issues were first recorded and never fired, because every
corpus tested had none: an empty list hid an unsafe shape.

A third, found while measuring a smaller corpus: a site that sent laboratory
messages and wrote reports but produced no imaging study had its street address
printed in every report header and never redacted, because imaging metadata was
the only place addresses were learned from. Its *name* was removed, which is
what made it hard to see — the header read `[INSTITUTION]` above an intact
street and city. Addresses are now also read from the line under an institution
the structured exports already named.

### `commissura whois`

```bash
commissura whois RSSMRA80A01X000Z --key-file ./commissura.key
```

```
  subject label                   8ac2e8cedbde
  directory                       sub-8ac2e8cedbde
  identifier, normalised          RSSMRA80A01X000Z
  key fingerprint                 bb0be87afcf8eb23
  de-identification rule version  1.1.0
```

**The identifier is validated and normalised first**, with exactly the rules
`build` uses, through the same function. That matters more than it looks: the
label this command prints has to be the label the dataset carries, or the search
it exists for comes back empty for the wrong reason. Case, surrounding and
internal whitespace, and compatibility-encoded digits all normalise. A value
that cannot key a subject — a placeholder, a wrong check character, the wrong
shape — is refused with exit code 2 and the diagnosis, rather than given a label
that corresponds to nobody.

**This is what an EHDS opt-out needs.** Somebody exercises their right to
object. You know exactly who they are; the datasets you already released
contain no name, no codice fiscale and no record number. The subject label is
the only handle that connects the two, and this derives it.

It reads nothing. The label comes from the identifier and the key, so the
answer is the same whether or not that person is in any dataset — which is
deliberate, because a command that *looked it up* would be answering "is this
person in this dataset?", a different and far more dangerous question. Check
the key fingerprint against the one in a dataset's manifest before trusting a
label against it.

Pipe the identifier instead of typing it when you would rather it stayed out of
your shell history. It is patient data, and the argument for keeping the key
off the command line applies to it too:

```bash
echo RSSMRA80A01X000Z | commissura whois --key-file ./commissura.key
```

**There is no command that goes the other way, and there will not be.** The
label is an HMAC truncated to twelve hex characters: no inverse exists to
implement, and the truncation means "the identifier for this label" is not even
a well-defined question. The only way to fake one is to enumerate the
identifier space and build a lookup table — which is precisely the attack this
design was chosen to resist, and a codice fiscale is derivable from a name, a
birth date, a birthplace and a sex, so that space is enumerable for anyone
somebody is actually interested in. A test asserts no such command exists.

### `commissura risk`

```bash
commissura risk ./dataset
```

```
  participants           10
  quasi-identifiers      age, sex
  minimum k              1
  below k=5              10 combination(s)
    k=1  age=22, sex=M
    k=1  age=36, sex=F
```

A dataset with no name in it can still identify somebody. If one participant is
the only 94-year-old woman in the cohort, that row is unique on attributes
nobody thinks of as identifiers.

`build` writes the report automatically, which is what `validate` looks for.
Note the honest result above: on ten participants with exact ages, minimum k is
1. Ten people cannot reach k=5 on age and sex together — a property of small
cohorts, not a defect, and the command reports the number rather than a verdict.

**Integrity is not completeness.** `verify` answers one question: do the files
match the digests the manifest records? A dataset still holding a record you
withdrew from the corpus verifies perfectly, because its bytes have not changed
since the manifest was written. The command says so in its own output. Four
different claims, and only the first two are things `verify` can speak to:

| Claim | Who establishes it |
| --- | --- |
| Integrity — the files are unchanged | `verify`, from the digests |
| Authenticity — the manifest is unedited | `verify --key-file`, from the HMAC |
| Completeness — the dataset holds what it should | Rebuilding from the current corpus |
| Correctness — it holds the right things | You, and the linkage issues |

**k-anonymity is a measurement, not a certificate, and this tool pseudonymises
rather than anonymises.** The distinction carries the whole legal weight:
pseudonymised data is still personal data under the GDPR, anonymised data is not.
The Commission's EHDS FAQ treats pseudonymisation and anonymisation as
alternatives and puts ultimate responsibility for either on the Health Data
Access Body, so a dataset built here is an input to that judgement and never the
judgement itself.

Not an Article 78 quality and utility label: those criteria are not published
yet.

#### Conformance is checked against the profile's own shapes

Not against this project's reading of the specification. `pyshacl` loads
HealthDCAT-AP Release 8's SHACL shapes, its `range.ttl`, and the DCAT-AP 3.0.0
shapes *and* class ranges, then judges the emitted description.

```bash
mkdir -p reference/healthdcat-ap && cd reference/healthdcat-ap
API=https://code.europa.eu/api/v4/projects/healthdataeu%2Fhealthdcat-ap/repository/files
EHDS=public%2Freleases%2Frelease-8%2Fhtml%2Fshacl%2FHealthDCAT-AP_validator%2Fconfig%2Frdf-validator%2Fehds
curl -so non-public-shapes.ttl "$API/$EHDS%2Fshapes%2Fnon-public-shapes.ttl/raw?ref=main"
curl -so range.ttl "$API/$EHDS%2Franges%2Frange.ttl/raw?ref=main"
DCATAP=https://semiceu.github.io/DCAT-AP/releases/3.0.0/html/shacl
curl -so dcat-ap-3.0.0-shapes.ttl "$DCATAP/shapes.ttl"
curl -so dcat-ap-3.0.0-range.ttl "$DCATAP/range.ttl"
```

Four files, each named explicitly with `-o`. The API endpoint ends in `/raw`, so
`curl -O` would save every one of them as `raw` and each would overwrite the
last — and the conformance test, which skips when a shape file is missing, would
report a tidy skip rather than a problem.

```bash
pytest tests/test_shacl_conformance.py
```

The test skips when the shapes are absent, so a clean checkout stays green.

**The first run found eleven distinct violations** that reading the cardinality
table had not revealed — six of them came from the imported DCAT-AP 3.0.0 shapes
and from `range.ttl`, which the health shapes do not contain. Among them: every
distribution needs a `dcat:accessURL`; both the HDAB and the publisher need a
`cv:contactPoint`; `dct:type` must be an IRI from an authority list and not a
string; record counts must be `xsd:nonNegativeInteger` and not the `xsd:integer`
a bare JSON number becomes; and a `healthCategory` reference must be a typed
`skos:Concept` carrying its label.

**The second round found six more**, and finding them needed a defect in the
profile to be worked around first. HealthDCAT-AP's `range.ttl` says in its own
comment that it imports DCAT-AP's class ranges "to ensure clear distinction
between reused and extended constraints". It does not: it declares itself as the
DCAT-AP range IRI and then `owl:imports` that same IRI, so the import is a
self-loop and brings in nothing. **84 class range constraints were therefore
never being checked.** Loading DCAT-AP's `range.ttl` by hand turned up six
failures, all the same shape of mistake: `sh:class` is satisfied by an
`rdf:type` triple *in the data graph*, and a validator does not dereference an
authority list to find one. So `dct:accessRights`, `dct:format`, `dct:type` and
`dcatap:applicableLegislation` all needed to carry their class inline, and
`dcat:contactPoint` needed to be a `vcard:Kind`.

That last one is worth keeping straight: DCAT-AP constrains the dataset's
`dcat:contactPoint` to `vcard:Kind`, while the HealthDCAT-AP shapes constrain an
agent's `cv:contactPoint` to `cv:ContactPoint`. Two profiles, two contact
models. Each is used where its own shapes ask for it; picking one and using it
everywhere is the tempting move and fails half the shapes.

Two findings are about the profiles rather than about this project. **Release 8's
published shapes are not valid SHACL**: an `sh:or` sits inside the `sh:property`
list with no `sh:path`, which no property shape may lack, and a strict engine
refuses the whole file. The test repairs it on the parsed graph — not by editing
the download — and a second test fails once upstream fixes it, so the workaround
cannot outlive the defect. The self-import above is pinned the same way.

And **five constraints in the DCAT-AP 3.0.0 shapes are inert**: they use
`sh:shape`, which belonged to a SHACL draft and is not in the standard, where
the parameter is `sh:node`. `CatalogRecord_Shape` uses both, two lines apart,
for the same inner shape. A conformant engine silently ignores the `sh:shape`
ones, so the date-type checks DCAT-AP intends on `dct:modified`,
`dcat:startDate` and `dcat:endDate` are not enforced by anything. Nothing here
depends on them; it is recorded because "conformant" means less than it looks in
that corner.

### Synthetic by construction

"Probably not real" is not good enough for clinical identifiers, so each one is
placed where no authority assigns:

| Identifier | Why it cannot be real |
| --- | --- |
| Codice fiscale | Place-of-birth code uses an `X` prefix; municipalities are assigned `A`–`M` and foreign states `Z`. The checksum is still valid, so the values exercise a real validator. |
| Telephone | Subscriber part starts with `0`, which is never assignable after an Italian area code. |
| Email | `.invalid` is reserved by RFC 2606 and can never be registered. |
| DICOM UID | The `2.25` arc holds UUIDs as integers, needs no registration, and collides with nobody. |
| Institutions | Invented names at invented addresses, every one marked `SINTETIC`. |

## Development

[![CI](https://github.com/jonathanmanca/commissura/actions/workflows/ci.yml/badge.svg)](https://github.com/jonathanmanca/commissura/actions/workflows/ci.yml)
[![Upstream dependencies](https://github.com/jonathanmanca/commissura/actions/workflows/upstream.yml/badge.svg)](https://github.com/jonathanmanca/commissura/actions/workflows/upstream.yml)

Every push and pull request to `main` runs `ruff check`, `ruff format --check`,
`mypy` and `pytest` on Python 3.11 to 3.14 on Ubuntu, and on 3.14 on Windows,
**installing from the lockfile**. It then builds the same dataset from the same
seed and the same key on Ubuntu and on Windows and **compares the per-file
digests**, because for a tool whose output is meant to be verified later,
reproducibility is a property worth proving rather than assuming.

Three things have to match for that comparison to mean anything, and all three
are pinned in the workflow: the seed, the key, and the *name* of the output
directory — `dct:identifier` is derived from it, so building into `ds_a` and
`ds_b` legitimately produces two different documents. That was found by running
the comparison locally before writing the job, which is the only reason it is
not the first thing the job reported.

The two badges mean different things on purpose. **CI** is the gate: it installs
the locked dependency set, so a red tick means the commit in front of it broke
something and not that the world moved. **Upstream dependencies** is a weekly
canary that ignores the lock and resolves freely on 3.11 and 3.14; a red tick
there means a newly published version of `typer`, `pydantic`, `ruff`, `mypy` or
`pyshacl` no longer works with this code. That is worth knowing and worth
blocking nobody's merge, which is why it is a separate workflow: a failure in it
would otherwise turn the CI badge red and the badge would stop meaning "this
code is good".

```bash
uv sync --locked --extra dev
```

```bash
pytest && ruff check . && ruff format --check . && mypy
```

`uv.lock` is committed and pins all 36 packages, so two people installing a
month apart get the same dependency set. `--locked` fails rather than silently
re-resolving when `pyproject.toml` and the lock disagree, which is what you want
in a checkout and in CI: a lock that quietly updates itself is not a lock. After
changing a dependency, refresh it with `uv lock` and commit the result.

This is not theoretical. The first `uv sync --locked` in this repository replaced
the already-installed `typer` 0.28.0 with 0.29.0 — two installs of the same
unchanged project, days apart, resolving differently, which is exactly the thing
a lockfile exists to stop happening silently.

`pytest` measures branch coverage on every run and fails below 99%. The
threshold is enforced in configuration rather than offered as a flag, because a
threshold that applies only when somebody remembers to ask for it is not one.
To skip it while iterating on a single test:

```bash
pytest --no-cov tests/test_hl7.py
```

It is a regression floor, not a target. Coverage says a line ran, not that it
was checked, so the suite is written to pin the decisions that are easy to undo
by accident: that `--defect-rate 0` reports no defects, that a clean corpus is
still hard to de-identify, that institution names carry a synthetic marker with
no exceptions, that HL7 files contain no line feed, and that `verify_corpus`
actually fails when a file is altered.

The floor is Python 3.11, and `mypy` is configured against it, so a standard
library call added in a later version is caught even when the tests run on a
newer interpreter — this is how `Path.read_text(newline=...)`, which is 3.13 and
later, was caught before it shipped. To exercise the floor itself:

```bash
uv run --python 3.11 pytest
```
