# commissura — security audit

Audit date: 2026-11-13. Commit audited: `27216df`. Audit only: no source file was
modified. Every finding below was reproduced against the working tree; where a
claim rests on reading the code rather than on a run, it says so.

All test data used was generated by `commissura generate`. No real patient data
was introduced at any point, and no finding here required any.

---

## 1. Executive summary

commissura is in good shape where it has been looked at, and the places it has
been looked at are the ones its author thought of. The cryptography is sound,
the key handling is careful, the output whitelists hold, the HTML escaping is
now complete, and the manifest no longer carries derived patient data. Four
sessions of adversarial work on *what the manifest says* have paid off.

The findings below are concentrated somewhere else: **in what happens when the
input is not what the generator produces.** Three of the four high-severity
findings are failures of *identity resolution* — the step before
de-identification — and they share one mechanism. A subject is keyed on a raw
string taken from the input with no validation, no normalisation and no conflict
detection. When two people arrive under one key they are merged; when one person
arrives under two keys they are split; and both happen with **zero linkage
issues recorded**, in a pipeline whose stated design is that "linkage is
accountable".

The most serious consequence is not mis-attribution. It is that a merge
**defeats the de-identification itself**. Targeted redaction removes the
identifiers the structured export declared *for that subject*; when two people
share a subject, only the first one's identity is known, so the second person's
name is never looked for. This audit produced a built dataset containing the
line `Paziente: FRANCESCA FONTANA` — a patient's full name, in plain text, in
the one field the scrubber exists to redact — from inputs that produced no
error, no warning and no linkage issue.

The fourth high finding is independent: a rebuild into an existing dataset
directory leaves the previous build's files in place, reports `conforms`, and
the integrity machinery then certifies the mixture as authentic. A data holder
acting on a patient's objection by removing records and rebuilding does not
remove them from the dataset.

**Production-readiness: not yet, and the gap is narrow and specific.** Nothing
here requires redesign. Findings 1, 2 and 4 are all the same missing guard —
validate the key, scope it, and refuse to resolve an ambiguity silently — and
the data needed is already parsed. Finding 3 is a build-lifecycle fix. None of
them touches the cryptography, the layout, the profile work or the public API
beyond adding new reported conditions.

| Severity | Count |
| --- | --- |
| Critical | 1 |
| High | 3 |
| Medium | 4 |
| Low | 4 |
| Informational | 2 |

## 2. Threat model

### What the tool is

A local command-line tool. A data holder runs it on a directory of files that
their own systems exported, and sends two of its outputs onward: the dataset and
`.deident/manifest.json`. The key stays with the holder.

### Assumed load

One operator running a CLI over a folder of files. Not a service, not
concurrent, not multi-tenant. Findings are judged against that: a TOCTOU race
between two simultaneous builds is not a finding here, while a wrong result on a
single sequential run is.

### Assets, in order of what their loss costs

1. **The secret key.** Compromise lets the holder of a dataset recompute every
   pseudonym from a candidate identifier list, which reverses the whole scheme.
2. **The input corpus.** Unredacted clinical records, on the holder's disk.
3. **The released dataset.** Pseudonymised, but still personal data under the
   GDPR, and the thing a permit governs.
4. **`.deident/manifest.json`.** Travels to a Health Data Access Body. Its value
   is entirely that its statements are true.
5. **Correct attribution.** Not usually modelled as a security asset, and this
   audit's conclusion is that here it is one: wrong attribution is both a data
   integrity failure and, as finding 1 shows, a route to disclosure.

### Adversaries considered

| Adversary | Capability | In scope |
| --- | --- | --- |
| Recipient of the dataset | Reads the dataset, has no key | Yes |
| Recipient of the dataset with auxiliary knowledge | Knows one true date, or one lab value, for one subject | Yes |
| Someone with write access to the release share | Can edit dataset files and the manifest; has no key | Yes |
| The holder's own operator, making a mistake | Full access, no malice | Yes — and this is where the findings are |
| An HDAB, acting correctly | Receives dataset and manifest | Yes, as a reader who must be able to trust the manifest |
| Key holder | Everything | Out of scope by design |
| Local attacker on the operator's machine | Reads the operator's own files | Out of scope: they already have the corpus |

### Trust boundaries

```
  hospital export                 operator's machine                  outward
  ───────────────                 ──────────────────                 ────────
  lab/*.hl7     ──┐
  reports/*.txt ──┼──► read_corpus ──► build_dataset ──► dataset/ ──────────►  data user
  imaging/*.json ─┘      ▲   ▲            ▲                 .deident/ ───────►  HDAB
                         │   │            │
    ▲ UNTRUSTED INPUT ───┘   │            └── key file  (never crosses outward)
      hostile or merely      │
      malformed              └── the boundary the findings are about
```

The input boundary is the one that matters. Everything downstream of
`read_corpus` is correct *given* that `read_corpus` resolved identity
correctly, and nothing downstream can detect that it did not.

## 4. Confirmed findings

### Finding 1 — A shared or placeholder national identifier merges two people into one subject, and the merge leaks a name

**Severity: Critical.** **Exploitability: no attacker needed — ordinary malformed input.**

**Where:** `src/commissura/read/corpus.py:505-513` (`read_corpus`),
`src/commissura/read/corpus.py:313` (`read_lab`, national identifier
extraction).

**What the code does.** A subject is created the first time a national
identifier is seen and keyed on that raw string:

```python
national_id = record.identity.national_id
subject = subjects.get(national_id)
if subject is None:
    subject = Subject(identity=record.identity)
    subjects[national_id] = subject
subject.labs.append(record)
```

Two things follow. The string is accepted without any format validation —
`read_lab` checks only that it is non-empty. And when a second record arrives
under the same key, **its `Identity` is discarded**: the subject keeps the
identity of whichever record was read first.

**Why this is not hypothetical.** Real HL7 exports fill an unavailable
identifier with a sentinel. `UNKNOWN`, `N/A`, `0`, `000000`, `NOCF`, a single
space that survives a partial strip — each of these appears in production
interfaces, and each is a non-empty string. Every patient whose codice fiscale
was unavailable arrives under one key and becomes one subject.

**The consequence is disclosure, not only mis-attribution.** The scrubber is
given `KnownIdentifiers` built from the subject's `Identity` — one name, one
codice fiscale, one record number. For a merged subject that is the *first*
person's identity. The second person's name is therefore not in the set of
strings to remove, and targeted redaction, by construction, does not look for
names it was not told about.

**Reproduction.** Two laboratory messages from a generated corpus, for two
different people, with both national identifiers replaced by `UNKNOWN`, plus the
second person's own report:

```
subjects linked: 1   linkage issues: 0
dataset written: 1 subject(s)

the first person's surname  'BIANCHI' appears in: []
the second person's surname 'FONTANA' appears in:
    ['sub-cc2d4031ebcf/ses-02/reports/sub-cc2d4031ebcf_ses-02_run-01_report.txt']

sub-cc2d4031ebcf/.../report.txt: Paziente: FRANCESCA FONTANA
```

The first person's name was removed correctly. That is what makes this hard to
see: the failure is selective, and the parts that worked look like the whole
thing working.

**What does and does not notice.** `validate` reports nothing — the dataset is
structurally perfect. `measure` *would* catch it on a generated corpus, because
the surname is a planted `PERSON_NAME` span; but no defect produces a
placeholder national identifier, so no generated corpus reaches this path. The
scrubber's residual-risk list fired here, reporting "2 unrecognised all-capitals
token(s) remain" — but only because this generator writes names in capitals. See
finding 6: in title case it reports nothing.

**Recommended mitigation.**

1. Validate the national identifier before it becomes a key. A codice fiscale
   has a defined 16-character shape and a check character; the project already
   has `identifiers.py` for exactly this kind of knowledge. A value that does
   not match is a `LinkageIssue`, not a subject.
2. Maintain a deny-list of sentinels (`UNKNOWN`, `N/A`, `NONE`, all-zero, all
   same character) and refuse them explicitly, because a check-character test
   alone will reject a *valid* foreign identifier too.
3. When a second record arrives under an existing key with a **materially
   different identity** — a different surname or a different birth date — that
   is a conflict, and the only safe answer is to refuse to merge and record it.
   Silently keeping the first identity is the current behaviour and is the
   actual defect.

**Residual risk after mitigation.** Two records for one person whose demographics
genuinely disagree (a corrected surname, a corrected birth date) would now be
reported rather than merged, which means more work for the operator. That is the
right trade: this project's own note on identifier normalisation already says "in
this direction a false match is far worse than a miss".

### Finding 2 — The medical record number is a global flat index with silent last-write-wins

**Severity: High.** **Exploitability: no attacker needed — the normal multi-institution case.**

**Where:** `src/commissura/read/corpus.py:496` (`by_mrn` declaration), `:515`
(assignment), `:528` (report fallback), `:550` (imaging linkage).

**What the code does.**

```python
by_mrn: dict[str, str] = {}
...
if record.identity.mrn:
    by_mrn[normalise_identifier(record.identity.mrn)] = national_id
```

One namespace for every record number in the corpus, and an unconditional
assignment. A medical record number is a *hospital's own* number; two hospitals
both number their patients from 1. So in any corpus assembled from more than one
site, collisions are not an edge case, they are the expected case.

On a collision, the later assignment wins — "later" meaning whichever filename
sorted last, which is arbitrary. Every imaging study carrying that `PatientID`,
and every report that falls back to record-number matching, then attaches to the
wrong person. **No `LinkageIssue` is recorded**: from the linker's point of view
the lookup succeeded.

**The information needed to prevent this is already parsed and then discarded.**
PID-3 carries the assigning authority in component 4 —
`1787493^^^PRESIDIO OSPEDALIERO SINTETICO VALLEDORO^MR` — MSH-4 carries the
sending facility, and `LabRecord.sending_facility` already holds it. The index
key simply does not use it.

**Reproduction.** Two laboratory messages for two people at two different
institutions, given the same record number, plus one imaging study carrying it:

```
  facility 'PRESIDIO OSPEDALIERO SINTETICO VALLEDORO'  MRN '1787493'  name 'GALLI'
  facility 'POLICLINICO UNIVERSITARIO SINTETICO PIETRALTA'  MRN '1787493'  name 'BIANCHI'

subjects linked : 2
linkage issues  : 0

  BIANCHI ALESSANDRO  mrn=1787493  -> imaging studies attached: 1
  GALLI MARTINA       mrn=1787493  -> imaging studies attached: 0
```

One patient's imaging study, released under another patient's subject label,
silently.

**A second path to the same outcome, at one site.** Two messages with the same
record number and different national identifiers — a renumbering, a merge, a
mistyped codice fiscale — collide identically, with no institution difference
needed.

**And `normalise_identifier` widens the collision surface.** It strips leading
zeros and folds case, so `0012345` and `12345` now collide where otherwise they
would not. The stripping is deliberate and documented (it recovers the
`imaging.mrn_format_drift` defect), and this audit is not asking for it to be
removed — but it should be scoped, so the stripping happens *within* an
institution rather than across all of them.

**Recommended mitigation.**

1. Key the index on `(normalise(assigning_authority_or_sending_facility),
   normalise(mrn))`. Read `(0008,0080) InstitutionName` on the imaging side —
   the generator already writes it and `ImagingRecord` already carries
   `institution_address`, so this is one more tag.
2. Keep a flat fallback for the single-site case, but use it **only when it is
   unambiguous**: if one normalised record number maps to two different national
   identifiers, every record resolving through it becomes a `LinkageIssue` with
   its own reason (`ambiguous_record_number`). This is the same shape of guard
   the project already applies to untyped PID-3 identifiers — "once a sender
   labels anything, an unlabelled identifier is something it chose not to
   label".

**Residual risk after mitigation.** An export whose imaging metadata omits
`InstitutionName` while its HL7 messages carry a facility cannot be scoped, and
would fall back to the ambiguity check. That is the correct failure: a reported
unlinked study is recoverable, a silently mis-attributed one is not.

### Finding 3 — A rebuild into an existing dataset directory keeps the old files, reports `conforms`, and is then certified authentic

**Severity: High.** **Exploitability: no attacker needed — the obvious way to re-run the tool.**

**Where:** `src/commissura/build/writer.py:341-399` (`build_dataset`),
`src/commissura/build/integrity.py:78` (`digest_tree`).

**What the code does.** `build_dataset` resolves `out`, then writes files into
it. There is no staging directory, no check that the destination is empty, no
record of what a previous build put there and no removal of anything. Files that
the current build does not overwrite simply remain. `digest_tree` then digests
**everything under the root**, so whatever remained is recorded in
`integrity.files` and covered by `manifest_hmac`.

**Reproduction A — two different cohorts, caught.**

```
build corpus A into ./mixed    -> subjects 4, Validation: conforms,  exit 0
build corpus B into ./mixed    -> subjects 4, Validation: DOES NOT CONFORM
                                  4 error(s), exit 1
subject directories present: 8      participants.tsv rows: 4
manifest says subjects_linked: 4    manifest digests 8 subject directories
commissura verify --key-file:  files checked 49, altered 0, missing 0, added 0,
                               manifest authentic, "INTACT"
```

`validate` catches this (`PT006` ×4, "directory … is not listed in
participants.tsv") and `build` exits 1. That is the mitigating half.

**Reproduction B — one withdrawn record, not caught.** This is the case that
matters, and it is the one a data holder will actually hit. A patient objects
under the EHDS, or an export is corrected; the holder removes the record from the
corpus and rebuilds:

```
build  (2 imaging studies in the corpus)   -> derivatives: 2 files
remove one imaging study from the corpus
rebuild into the same directory            -> Validation: conforms
                                              0 error(s), 0 warning(s), exit 0
                                           -> derivatives: 2 files

diff against a clean build of the same corpus:
  only in the rebuilt dataset: sub-c7ae7c18a196_ae96145dbc2137db_imaging.json

commissura verify --key-file: manifest authentic, "INTACT"
```

The withdrawn study is still in the released dataset. The build reported success
with a zero exit code. The manifest digests the stale file and the HMAC covers
it, so `verify` — the command whose entire purpose is to say "this is the dataset
the manifest describes" — answers yes, for as long as the dataset exists.

`PT006` cannot see this: the subject is still listed, so nothing is orphaned at
the level the rule checks. Nothing else looks.

**Why this is the most consequential of the four.** It is silent, it is the
expected way to use the tool a second time, and it defeats the one legal
mechanism the project is built around. A holder who believes they have acted on
an objection has not.

**Recommended mitigation.** In order of preference:

1. **Build into a staging directory and publish atomically.** Write to
   `<out>.commissura-partial-<n>`, validate, then replace. `Path.replace` is
   atomic for a file on both platforms but not for a non-empty directory on
   Windows, so the realistic form is: stage, then move the old root aside, then
   move the new one in, then remove the old. This also gives rollback on failure
   and removes the partial-dataset problem (finding 12) at the same time.
2. **At minimum, refuse a non-empty destination unless told.** A `--force`
   flag that removes a directory this tool recognises as its own output — one
   carrying `.deident/manifest.json` — and refuses anything else, so the flag
   cannot be aimed at an unrelated directory. Refusing rather than warning is
   the choice the project already made for `--report` inside the dataset, for
   the same reason: a warning on an otherwise-successful build is a warning
   nobody reads.
3. **Independently of either**, have `build` compare what it wrote against what
   is now in the tree and report any file it did not produce. That is a
   `DroppedRecord`-shaped fact — "the dataset contains something you did not
   hand over" — and it belongs in the manifest beside
   `records_not_in_dataset`.

**Do not** simply delete the destination. The prompt's own caution applies: an
operator who types `--out ~/Documents` must not lose their documents. Hence the
"recognises its own output" condition above.

### Finding 4 — Case or internal-whitespace variation in the national identifier splits one person into several subjects, and an opt-out can then miss them

**Severity: High.** **Exploitability: no attacker needed.**

**Where:** `src/commissura/read/corpus.py:313` and `:505-513`.

**What the code does.** The reader strips surrounding whitespace from the
national identifier — `_identifier_of_type` calls `.strip()`, and the PID-19
fallback is `pid.field(19).strip()`. It does nothing else. In particular
`normalise_identifier`, which exists in the same module and folds case, is
applied to **medical record numbers only** and never to the national identifier.

The asymmetry is backwards. The hospital-local, collision-prone identifier gets
aggressive normalisation that causes merges; the globally unique identifier that
every pseudonym derives from gets none, which causes splits.

**Reproduction.**

```
one person, BNCLSN82R26X136L in one message and bnclsn82r26x136l in the other:
   subjects linked : 2
   linkage issues  : 0
   subject national_id='BNCLSN82R26X136L' carrying 1 laboratory record(s)
   subject national_id='bnclsn82r26x136l' carrying 1 laboratory record(s)
```

Derivation is on the raw UTF-8 bytes, so each spelling yields a different label:

```
  as written          -> sub-25334ec64b59
  lowercase           -> sub-cacd552a7475
  non-breaking space  -> sub-a0740fde8971
```

(Surrounding-whitespace and Unicode-normalisation variants are also distinct,
but surrounding whitespace is stripped by the reader so it cannot arise in
practice, and a well-formed codice fiscale is ASCII. Both are listed for
completeness, not as live paths.)

**Consequences.**

- One person becomes two rows in `participants.tsv`, each with part of their
  record.
- Each fragment has its **own baseline**, since the baseline is the earliest
  event among the records that reached it. So `day_offset` values in the two
  fragments are anchored differently and no longer describe one timeline, which
  silently destroys the one property the offsets exist to preserve.
- `risk` computes k over an inflated participant count, making the cohort look
  less identifiable than it is.
- **`commissura whois` returns one label.** The command exists so a holder can
  act on an EHDS objection; it derives the label from the identifier as the
  operator types it. If the dataset holds that person under a second,
  differently-cased label, the opt-out misses those records and the holder has
  no way to know.

**Recommended mitigation.** Normalise the national identifier once, at the point
of parsing, with a transformation documented as safe for the identifier scheme —
for a codice fiscale, strip whitespace everywhere and uppercase, and nothing
more. Record the normalisation in the manifest, because a reader needs to know
that `whois` and `build` agree. This pairs with finding 1: validating the shape
and normalising it are the same edit.

### Finding 5 — `residual_risk.structural` is a fixed list that contradicts the dataset it is written into

**Severity: Medium.** **Exploitability: n/a — a false statement, not an attack.**

**Where:** `src/commissura/build/manifest.py:329-345`.

**What the code does.** Four prose strings, written unconditionally into every
manifest regardless of what the build observed. One of them is false whenever
`build` runs normally:

```
 * Quasi-identifier combinations are not assessed; no k-anonymity report has
   been produced for this dataset.
```

Meanwhile, in the same dataset, written by the same command moments earlier:

```
.deident/risk_report.json exists: True
   minimum_k = 1 over ['age', 'sex']
   digested into the manifest's own integrity list: True
```

The manifest denies the existence of a file it digests.

**And the warning that is true is never quantified.** With
`--defect-rate 1.0`, every imaging study carries `BurnedInAnnotation = YES`, the
dataset records `burned_in_annotation: true` on 4 of 4 studies — and `validate`
reports `conforms — 0 error(s), 0 warning(s)`, exit 0, while the manifest prints
the same generic sentence it would print for a dataset with none.

This is the identical failure mode the project diagnosed and fixed on
2026-11-10 for the per-modality field table — a static list that "can only
account for what somebody remembered to write down" — in a section of the same
file that was not revisited. The fix is the same: derive it.

**Recommended mitigation.**

1. Emit the k-anonymity line only when no risk report was written, and have it
   name the report when one was.
2. Replace the burned-in sentence with a count: how many studies in this dataset
   carry `BurnedInAnnotation = YES`, reported at zero when none do, which is the
   convention the field table already follows.
3. Add a `validate` rule at **warning** severity for any imaging metadata
   carrying `burned_in_annotation: true`. This is the one DICOM hazard the
   project's own design notes single out, and a dataset full of them currently
   validates clean.
4. Likewise, emit the defacing sentence only when the dataset actually contains
   head imaging.

### Finding 6 — The residual-risk detector only sees all-capitals tokens, so a name in title case leaves no trace

**Severity: Medium.** **Exploitability: no attacker needed.**

**Where:** `src/commissura/build/scrub.py:412` (`_assess_residual_risk`).

```python
capitalised = set(re.findall(r"\b[A-Z]{4,}\b", text))
```

**Reproduction.**

```
Paziente: FRANCESCA FONTANA  -> 1 residual risk: "2 unrecognised all-capitals token(s) remain"
Paziente: Francesca Fontana  -> 0 residual risks
Paziente: FONTANA Francesca  -> 1 residual risk: "1 unrecognised all-capitals token(s) remain"
```

**Why it matters.** The detector is the project's second line of defence — the
measurement that inspects the output knowing nothing about what was planted —
and it is calibrated to a convention this project's own generator invented. The
decision log of 2026-11-13 names `_REPORT_LABELS` as "*the* obstacle to using
this on real data" because it is written against the generator's own labels. The
residual detector has exactly the same dependency and the log does not mention
it. The failure modes differ in the worst way: an unrecognised label produces a
loud `unlinked_report` issue per file, while a title-case name produces silence.

Finding 1's leak was partially visible only because of this heuristic. In a real
hospital's title-case template it would have been completely silent.

**Recommended mitigation.** Do not reach for named entity recognition — the
project rejects it for good reasons. Two cheaper moves:

1. Widen the token pattern to include title case *after* a known header label
   (`Paziente:`, `Dott.`), where the grammar says a name belongs. Position, not
   classification.
2. State the limit in the manifest's residual-risk note: this detector assumes
   names are written in capitals, and reports nothing on a corpus that does not.
   A heuristic whose calibration is undocumented reads as a guarantee.

### Finding 7 — `Pseudonymiser` retains every national identifier, and its docstring says it does not

**Severity: Medium** (false claim about a privacy property) / **Low** (actual exposure).

**Where:** `src/commissura/deident/pseudonymise.py:131-132`, `:142-176`.

The docstring of `subject_label` states:

> `national_id`: The real identifier, such as a codice fiscale. It is used and
> discarded; nothing here retains it.

It is retained, twice:

```
internal state after one call:
  {'_subject_ids':     {'RSSMRA80A01X000A': '4e424f09e6f9'},
   '_issued_subjects': {'4e424f09e6f9': 'RSSMRA80A01X000A'}}
```

The forward map is a cache; the reverse map is the collision witness. Both hold
every national identifier in the corpus for the lifetime of the object, which is
the lifetime of the build.

**Exposure.** Low on its own — the process must hold the identifiers anyway to
read the messages, and `repr=False` keeps them out of a dataclass repr. The paths
that would surface them are a crash dump, a debugger session, or a test run with
`--showlocals`. The reason this is Medium rather than Low is the docstring: this
is the module the project's own documentation calls "the most consequential code
in the project", and a false statement about retention there is the kind of claim
a reviewer would rely on.

**Recommended mitigation.** The reverse map does not need the identifier. It
needs something that distinguishes two inputs that truncate to one label, and the
*untruncated* digest does that exactly:

```python
full = _derive(self.key, _DOMAIN_SUBJECT, national_id).hex()
label = full[:SUBJECT_ID_HEX_CHARS]
previous = self._issued_subjects.get(label)
if previous is not None and previous != full:
    raise ValueError(...)
self._issued_subjects[label] = full
```

Equivalent detection, nothing retained. The forward cache saves one HMAC per
repeat lookup — microseconds — and can be dropped, or keyed on `full` if a
caller profile justifies it. Then fix the docstring to describe whatever remains.

### Finding 8 — The project's headline claim is never checked by CI, and the check skips silently

**Severity: Medium.** **Exploitability: n/a — a verification gap.**

**Where:** `.github/workflows/ci.yml:68-70`, `tests/test_shacl_conformance.py`.

The claim *"commissura emits HealthDCAT-AP-conformant dataset descriptions"* is,
by the brief's own words, "worth more than any feature". It is verified by one
test, which runs only on the author's machine, and which **skips** when the shape
files under the gitignored `reference/` tree are absent. A skip prints as a dot
in a summary line that also says `passed`.

The project already knows this is dangerous. Its own log records: "a skip is a
silent failure mode", and separately that a conformance test which skipped
silently from the wrong working directory went unnoticed. The same shape remains,
one layer up.

The reason CI does not fetch the shapes is good and should stand: a gate must not
depend on `code.europa.eu` being up.

**Recommended mitigation.** Vendor the four files. HealthDCAT-AP is CC BY 4.0,
which permits redistribution with attribution; DCAT-AP's shapes are published by
SEMIC on the same terms. Commit them under `reference/` with a `NOTICE` entry and
their source URLs, un-gitignore that path, and let CI run the conformance test
offline against a pinned copy. This is precisely the argument the project already
accepted for transcribing the obligation table rather than fetching it:
"transcribing makes an upstream change a reviewable diff instead of a silent
behaviour change". Additionally, make the test **fail** rather than skip when the
shapes are missing in CI (`-m conformance` with a CI-only `--strict-markers`
gate, or an environment check), so absence can never read as success.

### Finding 9 — `read_key_file` discloses one byte of key material in an exception message

**Severity: Low.** **Exploitability: requires a malformed key file.**

**Where:** `src/commissura/deident/keys.py:264-267`.

```python
except (OSError, UnicodeDecodeError) as exc:
    raise InvalidKeyError(f"key file {path} could not be read: {exc}") from exc
```

A `UnicodeDecodeError` names the offending byte and its position. An operator who
stores raw 32-byte key material instead of hex — a plausible mistake, since
`write_key_file` writes hex but nothing stops a user creating the file another
way — gets:

```
key file ...\raw.key could not be read: 'ascii' codec can't decode byte 0x8f
in position 1: ordinal not in range(128)
```

That is `material[1] == 0x8f`, disclosed by value and index, into whatever caught
the message: a terminal, a CI log, a bug report.

One byte of 256 bits does not break the HMAC. It is reported because this module
is the one place where "key material must not leak through exceptions" is a
stated design goal, and because the fix is one line: do not interpolate the
decode error.

```python
except UnicodeDecodeError as exc:
    raise InvalidKeyError(
        f"key file {path} is not ASCII text; it should hold "
        f"{KEY_BYTES * 2} hex characters"
    ) from exc
```

Keep `from exc` — a chained traceback is local, and the operator benefits.
(If even that is unwanted, `from None`.)

### Finding 10 — `digest_tree` follows file symlinks, so the manifest can authenticate bytes the dataset does not contain

**Severity: Low.** **Reproduced: no — see below.**

**Where:** `src/commissura/build/integrity.py:86-88`.

```python
for path in sorted(root.rglob("*")):
    if not path.is_file():
        continue
```

Verified facts: on this interpreter (3.14.7) `Path.rglob` has
`recurse_symlinks=False`, so a directory symlink loop cannot cause unbounded
recursion — that part is safe. `Path.is_file` has `follow_symlinks=True`, so a
**file** symlink inside the dataset is treated as a regular file and digested as
the content of its target, wherever that lives. Nothing in the codebase calls
`is_symlink` anywhere.

Consequences, reasoned from the code rather than reproduced (Windows refused
symlink creation without elevation on the audit machine):

- A symlink present at build time is recorded in `integrity.files` with the
  digest of a file outside the dataset. The manifest then authenticates bytes the
  dataset does not own.
- Archiving the dataset stores a link, not the content. The recipient's `verify`
  either reads a dangling link (reported `missing`) or resolves to a different
  file on their machine (reported `altered`), in both cases for reasons unrelated
  to tampering — which erodes trust in the one signal that detects real tampering.
- A dataset containing a *directory* symlink would also let `--report` write
  outside the `resolve()`-based guard in `build/report.py:447` while still landing
  somewhere the dataset links to, and therefore somewhere `digest_tree` reaches.

`build` never creates a symlink, so this requires one to be placed in the tree.

**Recommended mitigation.** Use `path.is_file(follow_symlinks=False)`, and report
any symlink found under the dataset root as its own finding — a dataset meant to
be copied and archived should not contain one.

### Finding 11 — `SecretKey` equality is not constant time, while `.matches()` is

**Severity: Informational** under the stated load.

**Where:** `src/commissura/deident/keys.py:86` (`@dataclass(frozen=True, slots=True)`).

The dataclass generates `__eq__`, which compares `material` with ordinary `bytes`
equality and short-circuits on the first differing byte. `matches()` exists
immediately below and uses `hmac.compare_digest`. Two paths to the same question,
one safe and one not, with nothing steering a caller to the safe one.

```
__eq__ generated by dataclass: True
a == b     -> True  (plain bytes compare)
a.matches(b) -> True  (compare_digest)
```

No timing oracle exists in a local CLI, which is why this is Informational.
The fix is `eq=False` on the decorator, which removes the unsafe path entirely
and makes `matches` the only way to ask. Nothing in the codebase compares keys
with `==` today (checked), so this is free.

### Finding 12 — No staging or rollback: an interrupted build leaves a partial dataset

**Severity: Low.**

**Where:** `src/commissura/build/writer.py:341`.

Files are written in place as the build proceeds. An interruption — Ctrl-C, a
full disk, a permission error partway through — leaves a tree containing some
subjects and no manifest. `verify` on it raises `FileNotFoundError`, which is the
correct refusal, and `validate` reports it as non-conformant. So the failure is
*detectable*, which is why this is Low rather than higher.

It becomes more than cosmetic in combination with finding 3: a partial build into
a directory that already held a complete dataset leaves a tree whose manifest is
the **old** one, describing the old dataset, while the files are a mixture. The
old manifest's digests would then flag the new files as `added`, so `verify` does
report it — but the dataset on disk is in a state no one asked for and the fix is
not obvious.

Subsumed by finding 3's staging recommendation.

### Finding 13 — `accession()` has no collision check, unlike `subject_label()`

**Severity: Informational.**

**Where:** `src/commissura/deident/pseudonymise.py:265-280`.

`subject_label` truncates to 48 bits and raises on a collision, with a docstring
explaining that silently merging two people is far worse than failing.
`accession` truncates to 64 bits and performs no such check. 64 bits makes a
collision astronomically unlikely, so this is not a defect — it is noted because
the asymmetry is undocumented, and a reader who found the guard on one and not
the other would reasonably wonder which is the mistake. One sentence in the
docstring closes it.

### Finding 14 — `2.25.<112-bit integer>` is not a UUID rendering, which is what the arc is for

**Severity: Informational.**

**Where:** `src/commissura/deident/pseudonymise.py:260-263`.

The `2.25` arc is defined (ITU-T X.667 / ISO-IEC 9834-8) as a UUID rendered as a
single integer. The implementation takes 14 bytes of the digest, giving a 112-bit
integer — well-formed as a DICOM UID (39 characters, inside the 64-character
limit) and unique in practice, but not a UUID. A consumer that decodes `2.25`
OIDs back into UUIDs would get a wrong answer.

The comment in the code explains the 64-character reasoning, which is sound. The
honest options are to use all 128 bits (`int.from_bytes(digest[:16])`, giving at
most 39 digits plus the prefix — still inside the limit, which makes this nearly
free), or to say in the docstring that the arc is being used for its
registration-free property rather than as a UUID encoding.

## 5. Areas examined and found sound

Recorded because an audit that lists only problems tells the reader nothing about
coverage.

### 5.1 No path traversal from input into output

Every output path is composed from a pseudonymous label, a session index and a
run counter — `sub-<hex>/ses-NN/reports/sub-<hex>_ses-NN_run-NN_report.txt`.
No component of any output path derives from an input filename or an input field
value, so a corpus containing `../../etc/passwd.hl7` cannot write outside the
dataset. The imaging derivative filename embeds the *pseudonymised* accession
(16 hex characters), not the original. Confirmed by reading
`build/writer.py:_write_subject_*` and by inspecting a built tree.

### 5.2 The HTML report's escaping surface is complete

Every interpolation in `build/report.py` passes through `_esc`
(`html.escape(..., quote=True)`), including the two `class="tag {...}"`
attributes repaired in `27216df`. Grepped for the sinks `_esc` cannot protect —
`href`, `src`, `style=`, `url(`, `javascript:` — and there are none: no
attribute in the generated page takes a URL or inline CSS from data. So HTML
escaping is sufficient for every context the page actually has.

### 5.3 The output whitelists hold

The imaging branch emits seven keys and no more:

```json
{"study_uid": "2.25...", "series_uids": [...], "accession": "474390ff3196431c",
 "day_offset": 248, "modality": "CT", "burned_in_annotation": false,
 "source_patient_id_matched_by": "normalised medical record number"}
```

`PatientName`, `PatientID`, `PatientBirthDate`, `PatientAge`, `InstitutionName`,
`InstitutionAddress`, `SeriesDescription` and every private tag are dropped by
never being copied. The whitelist-not-blacklist discipline the brief describes is
real, and it is what makes the manifest's observed field table possible.

### 5.4 The integrity construction is sound

The split — anyone can check the per-file digests, only the key holder can check
`manifest_hmac` — is correctly implemented. `canonical_payload` removes exactly
one named field and serialises with sorted keys and minimal separators, so
reformatting does not break the tag while any content change does. The HMAC
covers `integrity.files`, so the pair is not separable: an edited report plus a
recomputed digest list fails the tag. Tested by the project's own suite and
re-read here. Findings 3 and 10 are about *what gets digested*, not about the
construction.

### 5.5 Key handling

`write_key_file` uses `os.open` with `O_EXCL` and mode `0o600`, so there is no
window in which the file is more permissive, and overwriting an existing key is
an explicit choice. `umask` can only remove bits, so the file can never be
created wider than `0600`. `_restrict_permissions` verifies the result and
reports honestly on Windows rather than claiming a protection it did not apply.
`resolve_key` has no implicit default path. No command anywhere accepts a key as
a value, enforced by a test over every registered command. `generate_key` uses
`secrets`. This is the best-handled part of the codebase.

### 5.6 Domain separation

Five prefixes — `subject|`, `offset|`, `uid|`, `accession|`, `manifest|` — all
defined in one module, all applied inside `_derive`, with the fingerprint using a
sixth, separate, versioned separator (`fingerprint|v1`) under a different
construction. Nothing can be replayed across roles and the manifest tag cannot
collide with a subject label. Correct, and the reasoning is written down.

### 5.7 Compliance wording

No GDPR-compliance claim appears anywhere. The README states that the tool
pseudonymises rather than anonymises, that pseudonymised data remains personal
data under the GDPR, and that `risk` is "a measurement, not a certificate". The
`risk` note contains the strings a test pins (`not a certificate of anonymity`,
`not reachable`). The HealthDCAT-AP claim is qualified where the profile's own
defects make "conformant" mean less than it looks. Phase 7 found nothing to
correct in the wording; finding 8 is about the *verification* of the conformance
claim, not its phrasing.

### 5.8 Packaging and supply chain

Two runtime dependencies, `typer` and `pydantic`, both genuinely imported
(`models.py`, `validate/findings.py`); `pyshacl` is correctly dev-only. A wheel
built with `uv build` installs into an empty virtual environment and all eleven
commands run. The wheel ships `py.typed` and 50 entries, with no test file, no
`reference/` material and no `.key` included. `uv.lock` is committed, CI installs
with `--locked`, and free resolution is a separate weekly canary with its own
badge.

## 6. Potential findings requiring further investigation

Stated as questions, because this audit did not settle them.

1. **Does any `LinkageIssue.detail` string carry patient data to the terminal?**
   The details no longer reach the manifest (fixed in `27216df`), and printing
   them to a terminal is a deliberate decision. But `read_lab` raises
   `ValueError` with messages this audit did not enumerate, and
   `unreadable_lab_message` carries `str(exc)` verbatim. Worth one pass over
   every `raise` in `read/` asking whether the message interpolates a field
   value.

2. **Is `_age_band` correct at the boundary?** Not examined. The ceiling at 89
   and `90+` above it is a de-identification invariant; an off-by-one would
   publish an exact age of 90.

3. **What happens on a corpus large enough to matter?** All testing here was on
   4 to 60 subjects. `measure` was quadratic until `27216df`; nothing confirms
   that `read_corpus`, `observe_corpus` and `digest_tree` are linear, and
   `digest_tree` runs twice per build-and-verify cycle over the whole tree.

4. **Does the corpus reader bound its own memory?** `ReportRecord.text` holds
   each report whole, and `read_corpus` holds every record for every subject for
   the duration. A hospital-scale export is a different load from the stated one,
   and the stated one is what this audit judged against.

5. **Which DCAT-AP version does the packaged validator's configuration load?**
   Still open in the brief. Unrelated to security; listed so it is not lost.

## 7. Residual risks after every recommendation here is implemented

These are properties of the design, not defects, and each is already documented
somewhere in the repository. They are gathered here because an auditor's reader
needs them in one place.

1. **Pseudonymisation is not anonymisation.** The output remains personal data
   under the GDPR and requires a permit and a secure processing environment. The
   tool cannot change this and does not claim to.
2. **Exact intervals are a re-identification channel, left open deliberately.**
   One true date for a subject, from any source, recovers their whole timeline.
3. **k is not reachable on continuous clinical values.** 98.1% of
   analyte-and-value combinations on a 60-subject corpus are shared by fewer
   than five subjects, and tripling the cohort moved that by two points.
4. **Targeted redaction cannot find a person named only in prose.** Measured at
   `--defect-rate 0.6`: 98.45% recall, with every survivor a person or
   institution named in a sentence and declared in no structured field.
5. **Pixel data is never inspected and head volumes are never defaced.**
   Finding 5 asks for this to be counted rather than merely stated.
6. **An HDAB without the key cannot prove the dataset was not tampered with.**
   Stated in `integrity.note` in the manifest itself.
7. **Key custody across institutions is unaddressed.** Deterministic HMAC makes
   cross-holder linkage work only if the key is shared, and this tool says
   nothing about how it would travel.
8. **The key holder can reverse everything.** Including forging
   `manifest_hmac`. This is the stated and accepted bound of the scheme.
